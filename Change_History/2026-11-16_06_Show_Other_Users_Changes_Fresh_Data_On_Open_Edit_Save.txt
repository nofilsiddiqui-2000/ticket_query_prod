WHY
---
Reported (Nofil, 2026-11-16, two accounts): B saves changes + comments on query Q. A had seen Q
before. A closes Q's tab, opens Q again, waits, clicks Edit Form: still the old history and old
values. Only F5 (browser refresh) shows B's changes.
Cause (CONFIRMED in the code + test): Power Apps keeps a copy of the data it has already read
from Dataverse in each browser and re-uses it. It is only thrown away by Refresh(<table>) or a
browser refresh. iQuery refreshes PNQ_Comments / PNQ_Backlogs only at the end of YOUR OWN save
(and on 2 list icons). Opening a query refreshes nothing, and Edit Form refreshes only
Query_Details (for the lock) and never re-reads the query into the tab.
Consequences: A sees old values and old history, edits and saves old values over B's changes,
and (LIKELY) gets a duplicate comment number (the save works out "last number + 1" from the
browser copy), which merges two history entries into one. A group save can reopen a part that
someone else closed in the meantime (it reads the parts' Status from the copy).
Full analysis + reviews: local draft files (_changes/, not in the repo).

THE FIX (agreed scope - 3 places, nothing else)
-----------------------------------------------
1. Edit Form (btnUpdate_1): refresh the 3 tables, read the query + details again into the tab
   (named columns, same list as record 05), clear fieldsUpdated, switch off "whole group" mode
   (isBatchEditing: false), SLA is worked out again. The comment box is NOT emptied (review 2). If the fresh Status is Closed -> message, no lock, no edit. Then the
   existing lock logic, unchanged. Take Over (from the "being edited by" pop-up) is not changed:
   it uses what was read when Edit Form was clicked (if B saves again while the pop-up is open,
   A misses that last save - Take Over re-read is on the bug list).
2. Opening a query (Gallery6, Gallery4_1, Gallery4_2; Gallery7 and Gallery7_1 only on the
   double-click): refresh the 3 tables + SLA reset, right after the clicked Doc No is captured.
   A new tab is built from the latest data; the history panel shows everyone's comments (it
   reads PNQ_Comments directly, also when the tab was already open). The fields of an ALREADY
   open tab are not re-read here (Edit Form does that) - so nothing you are typing is lost.
3. Save (HiddenSaveButton), start of the "Update Record" branch: Refresh(PNQ_Backlogs) and
   Refresh(PNQ_Comments), so the next comment number and the group's open/closed parts come
   from the server.

IMPACT / RISK
-------------
- New global variables: varEditDocNo (text), varEditReadOk (true/false). Used only in btnUpdate_1.
- No data source, flow, collection shape, App.OnStart or other screen is changed.
- Edit Form: the tab's queryDetails/tempQueryDetails/secondaryDetails/tempSecondaryDetails get the
  server values BEFORE editing starts. The button is only visible in view mode, so normal edits
  are never overwritten. Edge case: edits left over from an expired/invalid edit session
  (ContinueEditing_Button sets view mode but kept them) are now replaced by the server values -
  correct, someone else may have saved meanwhile.
- The comment box is NOT reset by Edit Form (it is one control shared by all tabs; a reset could
  erase a comment typed on another tab). Unchanged from today: typed text stays in the box when
  you switch tabs (pre-existing, on the bug list).
- Edit Form sets isBatchEditing: false (second small bug, OK'd by Nofil 2026-11-16): after
  "This editing session is no longer valid" (ContinueEditing_Button) the tab stayed in "whole
  group" mode, so the next Edit Form saved ALL open parts without Button9's group checks.
  Safe: Edit Form is only visible in view mode; Button9 (the only place that sets it to true) is
  only visible when isEditing && !isBatchEditing, i.e. after Edit Form. Side benefit: with the
  stale flag, Close Tab / the 60-min auto-close cleared the locks of the WHOLE group (also other
  users' locks); now only this part's lock.
- Not handled here -> record 07 (write/refresh error handling): a failed Refresh (the user then
  gets today's stale behaviour, not worse), a query with no Query_Details row, and the lock write
  not being checked before isEditing: true. All three are the same in production today.
- 'Modified On', PartNumber and PartDescription are not re-read (same as record 05; display only).
- Comment numbers: duplicates become much less likely, not impossible - two saves on the same
  query within a second or two can still get the same number (the number is worked out in the app).
- Edit Form on a query that is now Closed: the button disappears (its Visible already hides it
  for Closed) and a warning is shown. Before, A could edit a query that B had closed.
- Edit Form: if the query can't be read (network error / deleted): error message, no edit.
- Speed: each Refresh also re-queries the visible lists and labels that read that table (home
  list, dashboard counts, filter boxes, history panel) -> opening a query, Edit Form and Save
  are slower. Measure in T8. If too slow, the 3 Refresh lines can be put in Concurrent(...) later.
- Opening a query: the home list (Gallery6) and the history panel may change right after the
  click, because they now show the latest data. That is the point of the fix.
- Clicking a query whose tab is ALREADY open: the history and SLA become fresh, the fields stay
  as they were until Edit Form (accepted scope; Edit Form re-reads, and blocks a Closed query).
- Double-click detection in the search lists is unchanged (the refresh is inside the
  double-click branch, after the click was recognised).
- Not changed (on the bug list, separate records): re-reading an already-open tab when it is
  clicked in a list, Button9 (Edit whole group) refresh, save-time lock check, the same user in
  two browser tabs, group save clearing other users' locks, Reset & Refresh List icon.
- Only Studio can confirm that the types compile. If App Checker shows an ERROR on a changed
  control after pasting: don't publish, send a screenshot. Delegation: btnUpdate_1 ALREADY has
  2 delegation warnings (about Lower and LookUp, from the unchanged lock check). Any other
  delegation warning on a changed control is new -> screenshot.
